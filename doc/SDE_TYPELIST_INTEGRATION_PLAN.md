# SDE typelist integration plan (Frontier build 3502403)

Status: P0–P2 implemented; P3 assembly/construction hardening implemented with fabricator/station bindings on hold; P4 active NPC lanes and the build-versioned registry integrated, with NPC market and inter-system travel held until their transaction/movement runtimes exist. This is not a claim that every list is enforced. This plan uses the regenerated `_local/frontier-sde/3502403` snapshot created on 2026-09-22 (manifest `generatedAt` 2026-09-22T19:07:00.774Z). Its `typeLists.jsonl` has 420 unique IDs and SHA-256 `adef57d15d4163851a0e0a457d6a4a3de7b3740fba7193681d01f4b3a8d88583`. [The complete catalog](SDE_TYPELIST_CATALOG_3502403.md) enumerates **every entry**, including its name and rule shape. [The build-versioned consumer registry](SDE_TYPELIST_REGISTRY_3502403.json) classifies all 420 rows. Re-run the audit and registry generator when the installed-client build changes; list IDs and memberships are build data, not permanent game rules.

The source has 76 rule-empty lists, 31 unnamed lists, and 110 tag-only lists. Nineteen nested-list parents have no direct category/group/type includes. The current six-field game-store representation therefore gives 205 lists no positive rule: 76 truly empty plus 129 whose nonempty source rules are lost (110 tag-only and 19 nested-only). Three more nested parents retain some direct rules but lose most of their membership. All 621 nested references resolve to a source list and the nested graph has no cycles. Every referenced category, group, and type exists in this build's respective SDE file. `types.jsonl` itself carries `tags` (459 types have nonempty tags); all 15 distinct tag IDs referenced by typelists occur on at least one type. Duplicate inclusions occur in a few source rows, especially list 539, and should be deduplicated during normalization, not treated as separate permissions.

`requireAllFilteredTags` is nonzero on 110 rows. P1 verified the Frontier semantics directly from the installed build-3502403 `evetypes/__init__.pyc` (`GetTypeIDsFromTypeList`; SHA-256 `d7a19fc0ad74e933a0e790f4727e80da4d16127f9368d03c5d08a3c7375acea3`). The client unions category, group, type, tag, and nested-list includes; then subtracts category, group, type, tag, and nested-list excludes; then applies `filterByTags`. With `requireAllFilteredTags`, it intersects once per tag. Without it, the client calls `GetTypeIDsByGroups` on the filter values—surprising, but reproduced for parity. Thus a direct type inclusion **does not** override a group exclusion in Frontier. This differs from the [published EVE Online SDE rule](https://developers.eveonline.com/docs/guides/staticdata/), which is not the authority for this Frontier build. The [read-only client oracle](../tools/frontier-static/test/client-type-list-oracle.py) and [captured fixture](../server/tests/fixtures/frontierTypeListClient3502403.json) match the server evaluator across all 420 lists (catalog digest `351d5e35fdb51c1659de74fa060237599d0debf5e615b4fa1baf2bd923eb6288`).

## Current server coverage and gaps

The extractor emits the complete raw `typeLists.jsonl`. P0 makes `tools/DatabaseCreator/database-creator.ts` preserve names, descriptions, nested references, tag rules, `requireAllFilteredTags`, per-type tags, and source hashes in schema-v2 generated data. P1 makes `server/src/services/inventory/typeListAuthority.ts` the canonical Frontier evaluator. It lazily expands and caches membership by source-hash/build key and list ID, guards broken/cyclic nested lists, and keeps schema-v1 six-field stores readable. `server/src/services/dungeon/dungeonShipRestrictionResolver.ts` and `keeperService.ts` now use the same matcher, so restriction display and gate enforcement agree. Tag/nested membership requires a schema-v2 generated store; the active `_local/frontier-gameStore/3502403` has not been overwritten as part of this work.

Existing server uses include trade bans 36/142; ESS linkable ships 231; dungeon gate ship lists supplied by dungeon data; beacon links 300/946; structure compression 336; video fragments 492; mining lens targets 601/612; automatic moon output 611; invention skill adjustment 799; and NPC scan/interest lists 861/923/985. This is selective coverage, not proof that all 420 lists need bespoke gameplay code. List IDs **611, 799, and 946 are absent** in this recreated build. Their callers currently use group/ID fallbacks or a failed lookup; audit each fallback for intent and log a build-scoped diagnostic. Never silently reinterpret a missing list ID as a new list.

Other notable source-data caveats:

- List 600 (Frontier minable megastructure), 683 (free-fuel ships), and 864 (Feral network-node constructables) are empty. Their names cannot authorize mining, fuel, or construction; keep those paths gated by other explicit rules until the SDE populates them or a separate server-owned policy is approved.
- List 845 (named “All Frigates”) includes destroyer group 420; list 846 (named “All Cruisers”) includes combat-battlecruiser group 419, overlapping lists 848 and 849 respectively. Use membership, not names, and decide whether these overlaps are intentional before using them for fitting or hull restrictions.
- List 985 includes salvageable-wreckage group 5133. That is a target/interest classification, not evidence that salvage or recovery mechanics are implemented. The mining-compatible subset still needs tool and yield checks.
- Faction `typeMembership.typeListProfiles` is a server-authored NPC profile selector, not an SDE typelist ID. Keep those namespaces and validation separate; a faction profile may *refer to* an SDE list only through an explicit ID field and a build-validated policy.

## Implementation sequence

1. **P0 — data parity and visibility (implemented).** `clientTypeListRecord` and `typeRecord` preserve nested references, tags, tag filters, `requireAllFilteredTags`, names/descriptions, and build/hash metadata. The build audit rejects duplicate list IDs, dangling category/group/type/list references, nested cycles, and missing or empty *authoritative* runtime lists. It reports duplicate members, other empty lists, and optional hard-coded IDs absent from the snapshot (currently 611/799/946). It writes `type-list-audit.json` beside the generated store, including an added/removed/changed-ID diff when rebuilding an existing store. A temporary full build of 3502403 passed with 420 lists, 76 source-empty lists, 205 lists empty to the *old* basic-only matcher, zero integrity errors, and 92 warnings. The active `_local/frontier-gameStore/3502403` was not overwritten during verification; regenerate it through the normal deployment workflow to use the schema-v2 records. No matcher semantics or gameplay permissions changed in P0.
2. **P1 — one tested evaluator (implemented).** The server follows the installed Frontier client's include/exclude/filter order, not the EVE Online example. It expands nested and tag-derived membership with a recursion-safe cache keyed by build/source hashes and list ID, exposes `matchesTypeList`, `matchesAnyTypeList`, and expanded-membership diagnostics, and replaces the duplicate dungeon resolver logic. Synthetic tests cover empty, missing, nested, excluded-nested, tag-only, multi-tag, client-specific non-all filters, category/group/type conflicts, old schema, cycles, and type-ID-only contexts. A captured client oracle verifies all 420 build-3502403 lists. Unknown or broken lists fail closed; trade additionally denies unknown types or absent restriction lists.
3. **P2 — existing consumer repair (implemented).** Trade, dungeon, ESS/beacon, mining/compression, moon output, invention, fragments, and NPC scanning now use the canonical matcher at their server-side operation boundaries. The build-3502403 fixture verifies present P2 lists 36/142/231/300/336/492/599/601/612/613/861/923/985 and absent 611/799/946. Missing-list fallbacks are explicit, logged once per loaded build, and run only when the list is absent—not when a present list denies. These retain the legacy moon-material group 427, lower-invention-skill IDs, and carrier-beacon hull groups while list 946 is absent. Beacon list 300 no longer admits extra fallback hull groups when present. Trade checks nested contents before staging and again before settlement; ESS requires an in-space ship; structure compression passes list 336 into the mutation helper, while in-space compression retains its separate type-to-compressed-type mapping. Player and NPC mining share the Crude Extractor/lens/target guard at activation and cycle boundaries, support authored asteroid-lens lists 599/612/613, and authorize group-5133 wreckage by its mined source type rather than its different output material. Ordinary salvage/recovery remain unimplemented. The active schema-v1 game store was not overwritten; rebuild it normally for schema-v2 tag/nested rules.
4. **P3 — active assembly/construction implemented; fabricator/station binding on hold.** Native facility/blueprint pairs remain the production authority at preview, blueprint load, job start, and worker completion. The active runtime rejects docked station use and requires a constructed/activated assembly, owner or lane access, in-system ship proximity, exact materials, and output capacity. Player and NPC site planning share deployment range and collision-safe footprint rules; NPC construction places a site before material fulfilment, then realizes the assembly only after materials are present. The NPC material mutation now rechecks the durable ship assignment, live item owner/location/type/quantity, allowed owners, and duplicate IDs, so a stale or forged plan cannot spend another owner's cargo. Completion rechecks clearance against other assemblies before consuming deposits; a conflicted site remains intact for retry. Smart assembly state/ownership remains on the existing Sui reconciliation path. List 864 remains non-authoritative while empty. **Deferred:** no 565/597/606/607/609/784–812 binding was activated. These lists overlap only part of the native output set and carry no verified facility mapping; a broad binding would disable valid recipes. Station-centered crafting/industry has been removed, so station lists stay catalog-only unless that system is intentionally restored. A world contract records ownership/access, not mutable client typelist predicates without an explicit versioned design.
5. **P4 — active NPC lanes integrated; unsupported systems held.** Faction `typeMembership.sdeTypeListIDs` now accepts independent `hull`, `reinforcement`, `targetInterest`, and `loot` restrictions inherited from the fallback config and overridden per faction. Empty arrays preserve existing behavior; configured lists narrow it and missing, empty, excluded, or unresolved tag/nested membership fails closed. Hull eligibility is checked both when profiles are indexed and immediately before spawning generated or cached definitions. Drifter and coordinator reserve definitions are filtered, and reserve spawning rechecks reinforcement eligibility. Inventory-interest scanning checks before target selection and again before item transfer. Wreck generation filters only new loot rolls, not previously held cargo or fitted modules. The `market` field is reserved and rejects nonempty configuration because no NPC market transaction boundary exists. NPC stargate maintenance is active, but NPC inter-system gate/jump-drive movement is not; no travel/jump beacon list was bound by name alone. The [3502403 registry](SDE_TYPELIST_REGISTRY_3502403.json), reproducibly generated by `tools/frontier-static/build-type-list-registry.mjs`, classifies every row as `bound`, `client-only`, `unsupported-system`, `empty-authoring`, or `test-only` (13/3/323/76/5). `bound` is deliberately conservative: it means a directly verified static runtime consumer, not merely that a list could be selected later via faction config or dungeon data. The active schema-v1 game store still needs normal regeneration to use tag/nested rules from schema-v2 data. Fabricator/station bindings remain held under P3.

## Acceptance gates

- Regenerating build 3502403 yields 420 unique catalog rows with source fields intact, 621 valid nested references, and the same membership across import/restart. Future builds produce a diff of added/removed/changed lists and fail CI on dangling references or a missing list used as an authority.
- Shared matcher passes golden fixtures derived from the installed client for basic precedence, nested lists, and tags. Dungeon restriction display and gate enforcement agree on every tested ship.
- Active assembly industry preview, commit, and worker completion continue to agree on native facility/blueprint outputs. Generic, Synod, Exclave, nested station/fabricator, excluded-tag, and empty-list binding tests are deferred with the bindings; do not imply those lists currently authorize production. When bindings are later approved, pin them to a client build and test all three runtime boundaries before activation. Missing metadata must never broaden an activated binding.
- Existing trade, mining, NPC scanning, compression, and beacon tests pass with no regression. New tests cover the source-list overlaps and absent IDs above; unsupported/empty lists deny rather than silently permit.
- Faction SDE-list policies are opt-in, lane-specific, and checked at action boundaries; configured empty/missing lists never admit a type. The registry generator must reproduce all 420 statuses from the pinned source digest. Market and inter-system travel remain unsupported until an authoritative transaction/movement consumer and tests exist.

This plan changes server data and behavior only when each lane is implemented. It does not require a smart-contract deployment merely to consume the refreshed SDE.
