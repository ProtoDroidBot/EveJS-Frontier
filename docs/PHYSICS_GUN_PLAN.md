# Physics Gun (type 99999): full interaction plan

## Goal and scope

Make the fitted, ship-mounted Physics Gun feel like a Garry's Mod physics gun in Frontier: aim at a movable physical prop, grab it at the struck point, move it in three dimensions, change its distance, rotate and snap it, then drop, freeze, unfreeze, or launch it. The server owns selection, motion, collisions, resource use, and persistence. The client supplies intent and presentation. The initial target set is detached dungeon scenery, resource asteroids, and authored physical props; gameplay objects need an explicit allowlist.

This is an implementation plan, not a claim that these controls already work. The Unity sample's [interaction script](https://github.com/Laumania/Unity3d-PhysicsGun/blob/master/Unity3d-PhysicsGun/Assets/_PhysicsGunAssets/Scripts/PhysicsGunInteractionBehavior.cs) is a behavior reference for local hit anchors, hold distance, rotation, snapping, and freeze input. Its Unity `Rigidbody` operations cannot be copied into Frontier's networked Destiny simulation.

The present release is effectively a freeze: it restores a stationary ball. The current tether stores a world-space contact offset, which must become a local-space anchor before the prop can rotate without its grab point drifting.

## Player contract

| Action | Proposed input while 99999 is active | Server result |
| --- | --- | --- |
| Grab | Fire/hold on the first eligible collision | Detach once, reserve one prop, acknowledge its world ID and hit anchor, start beam and tether. |
| Move | Move aim and ship | Hold the original struck point on the aim ray at the selected distance, with ship clearance. |
| Distance | Wheel or dedicated increase/decrease binding while holding | Clamp requested hold distance to safe minimum and module range; never teleport the prop. |
| Rotate | Rotation modifier plus pointer/axis input | Rotate about the local hit anchor with bounded angular speed. Keep the same point under the beam. |
| Snap | Snap modifier while rotating; configurable increment, initially 15 degrees | Snap desired orientation; reject collision-producing poses. |
| Drop | Release fire | Release with bounded inherited linear/angular velocity, then let the prop coast and settle under the space physics rules. |
| Freeze | Secondary action while holding | Checkpoint the current valid pose, stop motion, persist `frozen=true`, release the lease. |
| Unfreeze | Secondary action on a frozen eligible world prop | Server-trace and validate again; persist `frozen=false`, activate free simulation. |
| Launch | Explicit launch binding while holding | Release with a capped impulse along the server-validated aim, paid for by a configured resource/cooldown cost. |

Bindings must be configurable and scoped to an active Physics Gun so they do not steal ordinary camera, fitting, or combat controls. The client patch should expose equivalent contextual controls if mouse bindings conflict with the EVE camera. Show acquired/blocked target, distance, rotation mode, freeze state, resource failure, and release reason. A denied request must not look successful.

## Authority and wire protocol

Keep `BeginHeldBeam`, `HeldBeamAimUpdate`, and `EndHeldBeam` as the existing fire path. Add one dedicated Physics Gun control RPC for distance, orientation, freeze, unfreeze, drop, and launch. Do not overload ordinary Cutting Laser or tractor-beam messages. Suggested payload: `{moduleID, leaseID, sequence, action, value}`. The server issues `leaseID` only after a successful grab, binds it to session, ship, fitted module, scene, and world entity, and rejects stale or reordered sequences. For unfreeze without a held object, the server performs its own first-hit trace rather than trusting a client-supplied entity ID. Return/notify `{accepted, reason, leaseID, worldEntityID, mode, pose, holdDistance}` so the owner can reconcile prediction and retarget selection after the source ball is replaced.

The server recomputes range, visibility, module online state, power, charge, capacitor, ship/bubble/dungeon scope, and object eligibility at grab and each active cycle. Clamp finite input and per-update distance/angle change. Give each world prop one scene-owned lease. Duplicate commands are idempotent; an invalid action leaves the last accepted state intact. Audit every pickup/launch/freeze decision with actor, module, world ID, and reason.

State machine: `idle -> acquiring -> held -> dropped/free -> settled`, with `held -> frozen` and `frozen -> free` transitions. `held -> released` must run exactly once on beam end, module removal/offline, resource failure, warp, jump, dock, disconnect, bubble/range loss, scene teardown, GM override, or server error. Restart never resumes a lease. It restores the last committed pose and a static safe state; the persisted `frozen` flag still records the intended game state.

## Server physics and persistence

1. Extract a shared detached-prop motion kernel for GM movement and Physics Gun translation. Keep the existing checkpoint-before-visible-step rule. Validate the lease and movement limits before detaching; if dynamic spawn fails after a committed detach, retain one durable stationary world prop and report the failed grab. Convert the hit point into `anchorLocal = inverse(rotation) * (hitPoint - center)`; each step recomputes the world anchor from current rotation. Target center equals aim-ray hold point minus the rotated local anchor.
2. Use a fixed simulation step, bounded accumulator, spring/damper linear force, angular controller, mass and inertia from authored data when valid, and conservative volume-derived fallbacks. Clamp force, acceleration, speed, torque, angular speed, prop radius, and per-tick displacement. The current fixed 1,500 m/s and 750 m/s² values are provisional safety caps, not final balance.
3. Sweep translated and rotated collision geometry. Use authored balls, boxes, capsules, and convex meshes where the server can resolve them; its current mesh-only path uses a bounding-radius approximation. Add rotational continuous collision tests or conservative substeps before allowing snap/rotation. Keep the carrier ship excluded only while holding; enforce ship clearance, other ships/props/scenery collisions, and no tunneling.
4. Separate outcomes: freeze creates a stationary persistent ball; drop/launch creates a free dynamic prop with bounded velocity. Add contact response, friction/damping, sleep threshold, and a maximum active lifetime so free props become static and durable. Decide ship/prop impact damage through a dedicated gameplay policy and test it; start with no combat damage until the policy is authored. Launch may use a stronger configured impulse but must obey the same collision and ownership limits.
5. Extend the detached record with a schema version and frozen state. Persist accepted position and rotation, plus any release metadata needed for crash recovery. Commit a final pose before freeze/drop/launch publication. A failed write restores the last durable pose, ends the lease, and reports failure. Keep the original source suppression scoped to its dungeon instance; never reuse the site-derived ID.
6. Make live tuning data driven: force, max mass/size, grab range, hold-distance limits, angular limits, snap step, launch impulse, capacitor/cycle cost, and cooldown. Preserve 99999 as a local ID until an upstream SDE entry exists; reject a source collision. Missing required balance data fails closed for new actions. Do not inherit Cutting Laser's mining or damage behavior as a fallback.

## Client and observer work

Extend the build-3502403 client patch narrowly around the Physics Gun held-beam controller. Preserve the existing Cutting Laser profile and `CreationModules` exterior placement object. Add scoped input, owner HUD, state notifications, and a retarget hook that transfers the selected source ID to the detached world ID after remove/add. Keep every optional client adapter step failure isolated so other UI and modules remain usable, per `tools/frontier-client/AGENTS.md`.

Display a beam from the fitted module to the current world-space hit anchor, target highlight and distance cue to the owner, and a moving-prop effect to observers in the bubble. Replicate accepted orientation alongside position; `GotoPoint` alone cannot express rotation. Use local prediction only for the owner's visual aim, with server pose correction. Start/stop FX exactly once across retarget, freeze, drop, launch, disconnect, and bubble transitions. Verify the actual staged client: the present unit tests cannot establish that selection, beam, rotation, or observer FX look correct.

## Client interpolation requirements

The normal space loop starts at 100 ms per tick (10 Hz); it must not be raised just to make a held prop look smooth. Today the tether throttles `GotoPoint` changes to at most one per 250 ms and refreshes the authoritative ball every 500 ms. Those messages remain useful for native Destiny movement and correction, but do not by themselves supply timely rotation samples or a continuous beam contact point. Add a lightweight, bubble-scoped pose stream for an actively held or freely moving Physics Gun prop. Publish only after the pose checkpoint succeeds, at most once per accepted scene step and normally no faster than 10 Hz; coalesce unchanged poses. If adaptive ticking slows the scene, the stream follows that cadence rather than inventing physics steps.

Each pose sample must identify the world entity and current lease/generation, carry a strictly increasing pose revision and server simulation timestamp, and include position, normalized orientation quaternion, linear/angular velocity (or an explicit unavailable marker), motion mode, and local hit anchor while held. The acquire/retarget message must pair the removed source ID with the new world ID and provide a full initial sample. Freeze, drop, launch, collision stop, sleep, removal, and bubble entry/exit need reliable state events with a final authoritative sample; intermediate pose deltas may be lossy because a newer full sample supersedes them. A newly interested observer receives a full current state before deltas. Destiny `GotoPoint` remains a native movement hint and ball refresh remains a correction path; the extra stream is a presentation contract and never grants movement authority to the client.

Maintain a small per-world-ID sample buffer keyed by generation and revision. Reject duplicates and old revisions, and reset the buffer on a new lease, entity replacement, scene change, or simulation-clock rebase. Estimate render time in **server simulation time**, respecting TiDi, then display a pose one to two received sample intervals behind that time. Interpolate position without overshooting the accepted path (linear is the safe fallback; velocity-based curves require clamping) and use shortest-path quaternion slerp for orientation. Compute the displayed beam endpoint from the *same* interpolated pose and rotated local hit anchor; the beam, prop graphic, selection highlight, and HUD must never use different pose samples. Do not interpolate across a source-ID/world-ID switch or a freeze/drop/launch state boundary.

For the firing pilot, render input and aim promptly using a local visual prediction from the latest accepted state, then converge to server samples with bounded corrections. Prediction cannot detach a prop, decide collisions, damage a target, or mark a freeze/launch successful before acknowledgment. Observers use interpolation only. Permit extrapolation for at most one expected sample interval, capped at 100 ms; after that, hold the last accepted pose and request/await a full refresh. Snap to a full authoritative pose on large error, collision stop, spawn, teleport, restart recovery, or lost continuity instead of slowly blending through scenery. Release and visibility events clear beam and buffer state exactly once.

Keep the extra stream limited to interested clients and active props, with a configured byte/rate budget; preserve the existing 500 ms ball refresh as a lower-rate reconciliation path. Measure bandwidth and client frame cost with multiple held props and observers. Tests must inject delayed, duplicated, reordered, and dropped samples; exercise 4, 10, and 20 Hz scene cadences and TiDi changes; verify normalized rotation, no path overshoot, stable contact-point/beam alignment, correct source-to-world retarget, and exact stop/snap behavior on every release mode. A live two-client pass must confirm the owner sees responsive aim, an observer sees smooth motion, and both converge to the same server pose after an interruption.

**Implementation status:** the current slice sends checkpointed pose samples only for an actively tethered Physics Gun prop and interpolates that prop's client model position and orientation; native Destiny balls retain gameplay authority. The existing release still settles the prop, and new rotation, drop, freeze, and launch controls remain in the broader roadmap. Owner prediction, selection retargeting, and beam-effect alignment require live client work. Interpolation for tractor beams, NPCs, drones, and other services is explicitly out of scope for this Physics Gun change.

## Delivery sequence and acceptance gates

1. **Contract and baseline:** document the state machine and balance defaults; add lease/control messages and explicit 99999 routing. Verify type/fitting, first-hit authority, no mining/damage fallback, and ordinary Cutting Laser/tractor-beam regression.
2. **Manipulation:** local hit anchor, adjustable distance, rotation, snap, and collision-safe motion. Verify moving ship and aim, eccentric/large props, rotated collision shapes, range clamps, invalid input, two competing guns, and checkpoint failure.
3. **Release modes:** persisted freeze/unfreeze, free drop, launch impulse, contact response, damping/sleep, and restart recovery. Verify release on every lifecycle edge, no duplicate source/world balls, asteroid resource continuity, dungeon reset/instance reuse, and crash on both sides of each durable write.
4. **Client presentation:** bindings, HUD, selected-target retarget, pose samples and interpolation, rotation and beam replication, observer delivery, and user-facing failure messages. Exercise the interpolation cases above in a live build-3502403 client with two pilots in one bubble and a third crossing a bubble boundary.
5. **Balance and rollout:** tune per-module limits from authored Dogma/SDE data or documented local defaults, test performance with many free props, add metrics for active leases/checkpoint latency/collision stops/denials, then gate the feature for staged deployment. Rebuild and sync `itemTypes`, `typeDogma`, and `creationModules`; run the stage verifier and live fitting/activation check.

Completion means a pilot can perform every action in the player contract against an eligible prop, other pilots see the same pose and effects, disallowed targets remain unchanged, and restart restores one durable world object at its last committed pose. Tests should include focused server physics/persistence cases, contract/client adapter tests, and a live two-client smoke pass.
