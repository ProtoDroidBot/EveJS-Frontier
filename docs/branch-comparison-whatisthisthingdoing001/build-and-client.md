# Build system and client tooling changes

[Back to the comparison report](../BRANCH_COMPARISON_whatisthisthingdoing001.md).

### TypeScript becomes the source of record

- Root `package.json` adds `build`, `build:production`, `build:server`, `build:tools`, `build:browser`, `build:tests`, and corresponding `typecheck:*` commands. `postinstall` builds the full tree; `pretest` also builds. Production compilation includes server, tooling, and browser code; server tests compile separately.
- New [tsconfig.json](../../tsconfig.json), [tsconfig.tools.json](../../tsconfig.tools.json), [tsconfig.tests.json](../../tsconfig.tests.json), and [tsconfig.browser.json](../../tsconfig.browser.json) target ES2022. Server/tooling use NodeNext module resolution, while the New Eden Store browser script remains a non-module browser script. Compilation emits `.js`/`.mjs` and source maps beside `.ts`/`.mts` sources, uses incremental caches under `node_modules/.cache/typescript`, disallows JavaScript source inputs, and stops emission on compiler errors. `strict` is explicitly `false`; this is not a strict-type-safety conversion.
- The migration covers the server, tests, test runners, Docker market database utility, certificate tooling, Config Editor, Database Creator, New Eden Store Editor, Frontier static tools, and contract exporter. Many converted files have no runtime change beyond compilation/import/type declarations. For example, [scripts/Tests/run-isolated-tests.ts](../../scripts/Tests/run-isolated-tests.ts) retains its prior JavaScript implementation, [frontier-test-files.ts](../../scripts/Tests/frontier-test-files.ts) retains emitted-JavaScript file discovery, and Config Editor/New Eden Store conversion changes mostly add types. The same-named tracked generated files remain in the endpoint diff, so raw line/file totals substantially overstate independent behavior changes.
- `.gitignore` now ignores generated JavaScript/MJS/maps and TypeScript build caches, with explicit exceptions for the authored type-list registry/audit files and one authority test. It also ignores local Elysian/Serenity/importer tooling, `.pnpm-store`, and `.tmp`, while allowing the new NPC Dogma workbench and its launcher.
- Root and server packages declare Node `>=24.11.0`. Root adds pinned TypeScript `5.9.3` and `@types/node` `24.13.3`, plus runtime dependencies `@mysten/sui` `^2.30.0` and `@noble/hashes` `^2.4.0`; server also adds `@mysten/sui` `^2.30.0`. Both lockfiles change accordingly.
- [server/package.json](../../server/package.json) adds build/typecheck commands and a `prestart` server compilation step. Server startup and launcher/entrypoint paths enable Node source maps.
- [tools/BuildTypeScript.ps1](../../tools/BuildTypeScript.ps1) and `.bat` install root development dependencies with `npm ci --include=dev` when the compiler is absent, then run the full build. This helper is invoked by the Windows server launcher, generic [StartServer.bat](../../StartServer.bat), certificate installation, Config Editor, Database Creator, and Store Editor launchers. The native setup wizard now checks for TypeScript and compiled server output and installs development dependencies explicitly.

### Docker changes

- [Dockerfile](../../Dockerfile) gains a separate `typescript-builder` stage. It installs root dependencies including development packages with scripts disabled, copies sources, runs `build:production`, and prunes development packages before copying the resulting application into the Node 24 runtime image. The separate server dependency stage still installs production server dependencies, including native modules.
- Rust registry/Git/target and npm/TypeScript caches use BuildKit cache mounts. Rust binaries are copied from the target cache into `/opt/artifacts` before transfer to the runtime stage, allowing cached target directories without losing final binaries.
- [.dockerignore](../../.dockerignore) expands the build context allowlist to root package/TypeScript files, scripts, tool sources, and new NPC/dungeon/landscape configuration. It excludes generated JavaScript/maps, Python caches, client grabs, icon caches, and other large local tooling trees. JavaScript is rebuilt inside the image.
- [compose.yaml](../../compose.yaml) explicitly enables `EVEJS_PERSISTENCE_WORKER=1` for the server. [docker/entrypoint.sh](../../docker/entrypoint.sh) enables source maps and supplies the same persistence-worker default in its dedicated server mode.

### Windows and macOS launch/setup behavior

- [PlayFrontier.ps1](../../PlayFrontier.ps1), [StartFrontierServer.ps1](../../StartFrontierServer.ps1), [StopFrontier.ps1](../../StopFrontier.ps1), and [scripts/Tests/run-frontier-server-tests.ts](../../scripts/Tests/run-frontier-server-tests.ts) change their default Frontier build from `3474408` to `3502403`. Setup/staging still discover the installed build. The macOS shell workflow remains on `3467658`; the shell scripts are not new Linux/Wine gameplay support. Both [PlayFrontier.ps1](../../PlayFrontier.ps1) and [PlayFrontier.sh](../../PlayFrontier.sh) add `/tenant=dev` to client launch arguments.
- [SetupFrontierWindows.ps1](../../SetupFrontierWindows.ps1) uses absolute npm prefixes and explicitly includes root dev dependencies. Existing snapshots or generated databases without `assets/collision/bundle.collision` are regenerated as an upgrade, even without `-ForceData`. Rebuilding generated data preserves an existing mutable runtime; the script warns when that runtime is unmarked, or when `-ForceData` leaves it in place.
- Windows and shell server launchers copy the generated manifest into `gameStore/manifest.json` and refresh generated assets when reusing a runtime. This makes new collision assets available without resetting mutable runtime data. Both set `EVEJS_COLLISION_BUNDLE_REQUIRED=1`. The Windows launcher additionally explicitly enables the persistence worker. The shell launcher installs the TypeScript compiler when absent, runs the build, and enables source maps.
- [StartServer.bat](../../StartServer.bat) now checks for [server/index.ts](../../server/index.ts), builds, and verifies server dependencies before database migration/creation. This moves dependency setup ahead of operations that need compiled/native server modules.
- Windows [StartFrontierServer.ps1](../../StartFrontierServer.ps1) now manages the Smart Assembly dApp together with the game server. Startup requires the [smart-assembly-control](../../smart-assembly-control) checkout, installed dependencies, pnpm, `.env.local`, `.deployment-source.json`, and localnet world deployment/feature files. It builds the dApp, checks port 443 in addition to existing game/service ports, and runs its `scripts/serve.mjs` at `https://dev.dapps.evefrontier.com` on loopback port 443. The dependency requirement applies to both foreground and background startup; there is no launcher option in this change to omit the dApp.
- The dApp gets separate stdout/stderr logs and a build-owned PID marker. Its process identity is validated using path, start time, and command line. Background startup cleans up both newly started processes if startup does not complete. Foreground startup now uses a child server process and a PID marker with `launchMode=foreground`, waits for it, and cleans up the dApp and matching markers on exit.
- [StopFrontier.ps1](../../StopFrontier.ps1) handles foreground/background server markers and dApp markers, reports their status, supports dry-run, removes stale records, and refuses to stop a PID that does not match its recorded process identity. Server-marker removal rechecks PID/start-time identity before deleting the marker. Runtime reset refuses active or stale dApp markers, as well as the existing server/listener checks.
- The Windows server launcher resolves `EVEJS_SUI_WORLD_CONFIG_PATH`, defaulting to `_local/frontier-world/<build>/world.private.json`. When synchronized world configuration is being used, it checks ready/localnet/build metadata, saved deployment/publication hashes when available, and the current local RPC chain identifier. Stale configurations direct the operator to `FrontierWorld.ps1 sync`. Explicit complete world IDs plus signer credentials, or explicitly disabled character provisioning, bypass this synchronized-config requirement. A missing synchronized file is not itself rejected by this specific preflight function; downstream provisioning/dApp requirements still apply.
- [StageFrontierClient.ps1](../../StageFrontierClient.ps1) now validates an existing stage against its recorded absolute source/cache paths before comparing it with the currently selected source. Status/dry-run can describe a stage from a different source; replacement requires `-Clean`. An intentionally base-synchronized source is protected from cleaning until restored. Existing stage verification accepts recorded synchronized hashes for the exact files intentionally copied back to that source.

### Local Sui world orchestration and operator commands

- New [FrontierWorld.ps1](../../FrontierWorld.ps1)/`.bat` provides Windows PowerShell 7 `sync`, `up`, `down`, `restart`, and `status` commands around the user's installed `efctl`. It resolves efctl from PATH or an explicit path, validates supported forwarded arguments, serializes operations with a mutex, checks Docker workspace ownership, and tracks `syncing`, `starting`, `stopping`, `ready`, `down`, and `error` states.
- The default workspace is this repository, with the new pinned [world-contracts](../../world-contracts) and [builder-scaffold](../../builder-scaffold) submodules; a third submodule supplies [smart-assembly-control](../../smart-assembly-control). [efctl.yaml](../../efctl.yaml) selects the ProtoDroidBot world-contracts `world-stuff-001` branch, builder-scaffold `main`, local host `127.0.0.1`, GraphQL enabled, frontend disabled, and PostgreSQL not exposed. The gitlinks pin actual commits independently of these branch labels.
- Synchronization validates stable deployment/publication snapshots, Sui addresses/private-key encoding, localnet chain identity, and assembly energy configuration. It writes `world.private.json` under the ignored per-build `_local/frontier-world` directory through the private-file helper with a current-user-only ACL. The private output includes current base-world IDs, the admin signer used by server provisioning, assembly energy metadata, and source artifact hashes.
- Versioned `world-features.v1.json` is validated and synchronized separately from base-world IDs. Legacy `npc-deployment.json` manifests are migrated deliberately, preserving compatible capabilities/faction policy and archiving the legacy destination. Invalid feature data leaves the synchronized world in an error state rather than presenting it as ready.
- Sync discovers SDE factions, reconciles missing unified/split faction configuration while preserving authored faction policy, tops up configured faction wallets, and invokes the dApp's `configure-local.mjs --network localnet --force`. `up` and `restart` sync after efctl succeeds. Dry-run and explicit testing/recovery skip flags exist for RPC validation, Docker ownership, funding, and dApp configuration.
- Root npm scripts add the world wrapper and dApp install/HTTPS setup/configure/build/test/start/restart commands. `frontier:npc:fund` builds tooling then runs [scripts/FrontierWorld/fund-npc-factions.ts](../../scripts/FrontierWorld/fund-npc-factions.ts)'s emitted script, with optional world/faction paths and dry-run. It requires a ready synchronized localnet whose chain matches the live chain, then delegates wallet funding to the server's faction-funding implementation and prints summary counts.
- `frontier:npc:verify` runs the new [scripts/Tests/verify-npc-deployment.ts](../../scripts/Tests/verify-npc-deployment.ts): a read-only localnet transaction simulation with transaction checks enabled, no signing or submission. Separately, [tools/verifyNpcFactionGasSponsorship.mts](../../tools/verifyNpcFactionGasSponsorship.mts) is a manual localnet smoke tool that does submit an admin-authorized, faction-gas-sponsored transaction after testing both denied faction-only and successful sponsored dry-runs. These tools have materially different side effects.

New comparison JSON records and [docs/FRONTIER_BUILD_3488090.md](../../docs/FRONTIER_BUILD_3488090.md) / [docs/FRONTIER_BUILD_3502403.md](../../docs/FRONTIER_BUILD_3502403.md) record source hashes, descriptor/static comparisons, historical offline verification, and outstanding live acceptance. The docs expressly describe port candidates; their historical test counts are not evidence of testing in this report.

This is an explicit in-place operation separate from ordinary staged-client patching.

- New `map-upgrade` and `adapters-upgrade` commands upgrade a completed build-3502403 stage using owned backups, manifest/hash refresh, post-verification, and rollback on failure. New `sync-base` and `restore-base` intentionally copy/restore the completed stage's native blue module, `code.ccp`, manifest, and two CA bundles to/from its recorded original source. Base-sync originals live under `_local/frontier-client-source-backups/<build>` and sourceSync records bind the exact target hashes and backup; this changes the source installation only when explicitly invoked.
- [patch_npc_interaction_stage.py](../../tools/frontier-client/patch_npc_interaction_stage.py), [patch_npc_primary_stage.py](../../tools/frontier-client/patch_npc_primary_stage.py), and [reconcile_npc_order_stage.py](../../tools/frontier-client/reconcile_npc_order_stage.py) provide focused completed-stage update/reconciliation paths for NPC interaction/menu changes and their recorded archive/manifest state.
- The client subtree gains [AGENTS.md](../../tools/frontier-client/AGENTS.md), requiring small independent exception boundaries for injected client operations, continued access to native fallbacks and other menu/list entries, and explicit handling of denied mutations.

### Static extraction, database generation, and integrity tools

- Discovery now requires `bin64/bundle.collision`. Extraction adds `typelist.fsdbinary`/`typeLists.jsonl` and captures `bundle.collision` as `assets/collision/bundle.collision`. It parses the collision FlatBuffer sufficiently to validate offsets, require items and strictly ordered collision IDs, and record item/mesh/uniform counts and ID bounds. Manifest data records schema, bytes, SHA-256, and source identity.
- [validate-frontier-static.mts](../../tools/frontier-static/validate-frontier-static.mts) now requires that collision asset, verifies its path stays within the snapshot, checks size/hash/source identity, reparses it, and compares all recorded counts/bounds. [build-frontier-database.mts](../../tools/frontier-static/build-frontier-database.mts) installs the asset into the generated gameStore with containment and hash/size checks, adds it to the generated manifest, and includes collision information in validation output. Old snapshots without this metadata/assets require refresh.
- [tools/DatabaseCreator/database-creator.ts](../../tools/DatabaseCreator/database-creator.ts) adds required tables for `creationPresets`, `npcPilotIdentities`, `stargateRuntimeState`, `remoteSystemScans`, and `systemSignatureEvents`. NPC identity placeholders initialize version, reserved next-character ID, pilot/slot/faction maps. System records retain frost line, habitable-zone values, and star temperature for runtime environmental behavior.
- Generated item records now retain tags. `clientTypeLists` becomes schema version 2, retaining names/descriptions/display-name IDs, nested included/excluded list IDs, tag inclusion/exclusion/filter rules, and all-filtered-tags mode. Generated source/manifest data hashes both type-list and type inputs. `typeDogma` retains full `effectEntries` with `isDefault` alongside flat effect IDs.
- For Frontier `3502403`, generation adds local Physics Gun type `99999` by cloning Cutting Laser `95317` type/dogma/Creation data with a generic weapon module placement contract; collisions with existing SDE IDs or missing source rows fail. Database validation checks the exact clone relationship and adjusts expected row counts. Rift authority validation expands to `3488090` and `3502403`.
- [type-list-audit.mts](../../tools/frontier-static/type-list-audit.mts) validates list IDs, category/group/type/list references, rule arrays, recursive list structure, tag references, and declared runtime bindings; it reports missing/empty bindings and compares new source data with prior generated data. Database generation fails on integrity errors, writes `type-list-audit.json`, and reports warnings without silently remapping list IDs. Required NPC lists `861`, `923`, and `985` are explicitly checked in generated data.
- [build-type-list-registry.mjs](../../tools/frontier-static/build-type-list-registry.mjs) adds an exact-hash build-3502403 registry of 420 lists, classifying verified runtime bindings, client-only, unsupported-system, empty-authoring, and test-only lists. It supports generation and `--check`; related catalog/registry/integration-plan documentation is added.
- [audit-frontier-references.mts](../../tools/frontier-static/audit-frontier-references.mts), exposed as `npm run frontier:references`, checks declared cross-file SDE relationships, including nested values and map-key IDs. It supports text/JSON output, rule listing, limits on reported issues, passed/unmapped reporting, and strict handling of unmapped reference fields.
- [extract-industry-static.py](../../tools/frontier-static/extract-industry-static.py) reads the client's native Python 3.12 Industry blueprint/facility loaders and indexed resources and writes a compact reviewable server snapshot containing build and source hashes. It requires the local client/cache and does not download or patch the client.
- `lib/frontier-python.mts` adds Linux pure-Python 3.12 contract export and an explicit Wine + Windows Python 3.12 static-extraction path selected via `EVEJS_FRONTIER_WINE` / `EVEJS_FRONTIER_PYTHON312`. Pure-Python execution is opt-in for contract export, not a substitute for native FSD loaders. On Windows the external interpreter keeps its own standard library, clears inherited PYTHONPATH, adds client paths after initialization, registers the DLL directory, and probes `python312.exe` in addition to prior candidates. [export-frontier-contracts.mts](../../tools/frontier-contracts/export-frontier-contracts.mts) opts into portable descriptor extraction.

### Elysian NPC Dogma Workbench

- New [tools/ElysianNpcDogma/](../../tools/ElysianNpcDogma/) is a Python package with PySide6 desktop UI and CLI. [tools/Launch-Elysian-NPC-Dogma.bat](../../tools/Launch-Elysian-NPC-Dogma.bat) and the package-local launcher route through the shared ElysianToolSuite bootstrap. It requires Python >=3.11, PySide6 >=6.8,<7, and `elysian-fsd==0.1.0`; pytest is an optional development dependency.
- Its catalog combines client type/dogma definitions with server profile/spawn references, distinguishing published, hidden, configured, and spawn-used NPC hulls, with player-hull source suggestions. Change projects save selected attribute/effect edits without replacing the entire type record, including effect `isDefault` metadata.
- CLI operations are `scan`, `create`, `validate`, `diff`, `compile`, `apply`, `rollback`, and `gui`; project files use `.elysiannpcdogma`. Copy presets cover fuel, slots, CPU/power, hardpoints, rigs, durability, navigation, targeting, drones, and fighters.
- Compilation validates the project and current source, requires native encoder verification, compiles a candidate FSD resource, then rereads edited rows through the native loader and compares them with requested records. Deployment bundles include both client typeDogma and server `typeDogma/data.json`, use the Elysian owned-transaction mechanism, and record client/server restart requirements. Rollback restores the active bundle.
- New workbench unit tests cover state/usage inventory, selected attribute/effect editing, retained effect metadata in documents/server projections, and project round-trip serialization. These tests were inspected, not run.

### Concrete limitations found while documenting

- [tools/frontier-static/build-type-list-registry.mjs](../../tools/frontier-static/build-type-list-registry.mjs) still targets `doc/SDE_TYPELIST_REGISTRY_3502403.json`, while the tracked file is [docs/SDE_TYPELIST_REGISTRY_3502403.json](../../docs/SDE_TYPELIST_REGISTRY_3502403.json) after the documentation relocation. Its default generation/check path therefore does not address the relocated file. This report records the discrepancy without changing code.
- The NPC Dogma launchers reference `tools/ElysianToolSuite/Bootstrap.ps1`, and the package imports `elysian_fsd`; neither ElysianToolSuite nor ElysianFSD is included as a tracked directory/submodule in this endpoint tree. The branch explicitly ignores those sibling tool families. A clean checkout therefore needs those external/local dependencies before the launcher/workbench can function.
- New Windows normal startup has additional dApp/pnpm/localnet-configuration prerequisites. The shell launcher does not gain equivalent dApp/world orchestration. Client docs preserve the distinction between offline exact-build verification and live game acceptance; historical Windows smoke evidence covers `3474408`, while the live-accepted macOS target remains `3467658`. Build `3502403` remains a candidate.
