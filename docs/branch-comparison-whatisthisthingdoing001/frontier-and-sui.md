# Frontier assemblies industry and Sui changes

[Back to the comparison report](../BRANCH_COMPARISON_whatisthisthingdoing001.md).

### Baseline and overall behavior change

Upstream already had native Frontier deployment/construction, basic assembly state changes, paired-gate travel, Smart Storage transfers, Network Node fuel configuration/transfers, Creation services, and a minimal Industry service. The branch substantially expands those systems and introduces an integrated Sui Localnet bridge. Industry changes from an idle details response with no blueprint or stored contents into durable inventory, recipes, production, and configurable parallel lanes. Completed assemblies can now be mirrored to chain; storage, Industry, energy and gate operations are also exposed to a wallet-authenticated dApp. Local gameplay commits and confirmed chain convergence are explicitly separate outcomes.

Primary evidence: [server/src/services/frontier/industryService.ts](../../server/src/services/frontier/industryService.ts), [deploymentRuntime.ts](../../server/src/services/frontier/deploymentRuntime.ts), [smartAssemblyService.ts](../../server/src/services/frontier/smartAssemblyService.ts), [smartStorageUnitRuntime.ts](../../server/src/services/frontier/smartStorageUnitRuntime.ts), [networkNodeFuelRuntime.ts](../../server/src/services/frontier/networkNodeFuelRuntime.ts), and all newly added `sui*.ts` modules in that directory.

### World deployment lifecycle and added repositories

[FrontierWorld.ps1](../../FrontierWorld.ps1) and its `.bat` wrapper add `sync`, `up`, `down`, `restart`, `status`, and `-DryRun`. They resolve the installed `efctl.exe`, use an explicit workspace/config path, serialize lifecycle operations through a host-global mutex, and validate ownership of fixed-name Docker containers before operating on the Localnet. The checked-in [efctl.yaml](../../efctl.yaml) points to the forked contracts/scaffold repositories, enables GraphQL, disables the optional frontend by default, binds to `127.0.0.1`, and does not expose Postgres.

The wrapper reads a stable snapshot of deployment/publication artifacts, validates canonical Sui IDs, the live chain ID, a checksum-valid Ed25519 admin key, and the assembly-energy manifest. It atomically writes an ignored, access-restricted `_local/frontier-world/<build>/world.private.json` and a public `world-features.v1.json`. Explicit `EVEJS_SUI_*` overrides remain supported. Transitional/error states prevent runtime reuse of stale world configuration. Sync is separate from game-store creation and server startup.

Feature identity is now split into current call-package address, stable type origin, and shared registry; it is not inferred from the base-world package. [suiNpcWorldConfig.ts](../../server/src/services/frontier/suiNpcWorldConfig.ts), [suiIndustryDeployment.ts](../../server/src/services/frontier/suiIndustryDeployment.ts), and the PowerShell synchronizer validate independent capability records and migrate older `npc-deployment.json` schemas. Current source recognizes ten feature capabilities: NPC, assembly access, catapult, Smart Industry, transponder, action queue, Industry actions, logistics actions, infrastructure actions, and automation. Missing/unavailable capabilities do not disable unrelated complete records. Historical incomplete triples are named in migration output.

Faction policy files separate global package identities from each faction's capabilities, canonical identity, transponder configuration, type selectors/overrides, contacts, leadership, commanders, and starting region/system fallback. Sync can discover missing numeric SDE factions and append missing authored/synchronized entries without replacing existing authored faction policy. It tops each configured faction wallet up to the configured common minimum from the admin account, optionally using the Localnet faucet to fund the admin first. [scripts/FrontierWorld/fund-npc-factions.ts](../../scripts/FrontierWorld/fund-npc-factions.ts) and [suiNpcFactionFunding.ts](../../server/src/services/frontier/suiNpcFactionFunding.ts) implement that funding flow. A missing/invalid dApp checkout or deployment manifest makes synchronization fail; successful sync runs the dApp's public configuration generator against the same contracts checkout.

### Character and NPC identities on Sui

New [suiGrpcClient.ts](../../server/src/services/frontier/suiGrpcClient.ts) and [suiCharacterProvisioning.ts](../../server/src/services/frontier/suiCharacterProvisioning.ts) supply the Localnet client, deterministic development player-wallet derivation, deterministic Character object identity, `character::create_character` transaction creation, chain/deployment checks, serialized admin submissions, and reconciliation of already-created or uncertain identities. [charService.ts](../../server/src/services/character/charService.ts) records provisioning status and prepared transaction material, distinguishes confirmed versus reconciliation-required characters, and integrates provisioning/recovery with Frontier creation/selection. An uncertain chain response is not treated as proof that no character was created.

NPC provisioning is separate: [suiNpcCharacterProvisioning.ts](../../server/src/services/frontier/suiNpcCharacterProvisioning.ts), [suiNpcProfile.ts](../../server/src/services/frontier/suiNpcProfile.ts), and [suiNpcIdentitySync.ts](../../server/src/services/frontier/suiNpcIdentitySync.ts) bind persistent NPC pilot identities to canonical faction wallets, Characters and NPC profiles. The worker runs in bounded batches, retries with backoff, checks world changes, and reconciles incarnation, active entity and death counters. `suiNpcCharacterProvisioningEnabled`/`EVEJS_SUI_NPC_CHARACTER_PROVISIONING_ENABLED` controls this integration alongside the Frontier profile and persistent-NPC identity configuration. NPC faction funding and gas sponsorship are explicit parts of the bridge rather than fabricated player sessions.

### Automatic assembly synchronization and transaction recovery

The new [suiAssemblySync.ts](../../server/src/services/frontier/suiAssemblySync.ts) worker starts from [server/index.ts](../../server/index.ts) after store initialization, defaults to a serialized five-second reconciliation loop, and is disabled for non-Frontier/isolated-test profiles or through `EVEJS_SUI_ASSEMBLY_SYNC_ENABLED=false`. An empty store causes no assembly/character creation. It snapshots completed chain-enabled Network Nodes, storage, gates, turrets and generic assemblies, resolving local IDs, owner Characters, locations, fuel, status, links and inventories into deterministic on-chain identities.

[suiAssemblySnapshot.ts](../../server/src/services/frontier/suiAssemblySnapshot.ts), [suiAssemblyChain.ts](../../server/src/services/frontier/suiAssemblyChain.ts), and [suiAssemblyContents.ts](../../server/src/services/frontier/suiAssemblyContents.ts) implement validation, anchoring, state/fuel/inventory reconciliation, reciprocal gate links, and removal of assemblies that this runtime previously tracked. Generic assemblies acquire the relevant feature sidecars for catapults/Industry. Owner and visitor inventories remain distinct and are aggregated by type for the chain representation. Capacity/volume use integer micro-cubic-metre conversion. Removal orders cleanup of contents, links, fuel and dependencies before deleting tracked objects; it does not sweep unrelated chain objects.

[suiAssemblyTransactions.ts](../../server/src/services/frontier/suiAssemblyTransactions.ts) journals signed bytes and signatures before submission, records confirmed digests, and reconciles or resubmits the exact bytes after ambiguous outcomes/restart. [suiAssemblySupervisor.ts](../../server/src/services/frontier/suiAssemblySupervisor.ts) and its child worker enforce serialized admission, bounded queues/timeouts, leases, journal revision checks and process recovery. Default controls include a 64-operation queue, a 10-second RPC timeout, 30-second admission timeout and 120-second lease, with `EVEJS_SUI_ASSEMBLY_*` overrides. Chain status reads and writes use the same serialized boundary, and snapshots are rechecked before new transactions so stale scans cannot authorize a fresh mutation.

New [suiAssemblyState.ts](../../server/src/services/frontier/suiAssemblyState.ts) separates desired local state from confirmed chain state and records explicit state intents. Storage, Industry and gate sync bridges expose `disabled`, `pending`, `synced` and `error`; a successful local write is not enough for `synced`. Fresh matching chain reads and no uncertain pending transaction are required. Errors are visible/retried without rolling back already-committed gameplay.

Important constraints remain: deterministic deleted object IDs cannot simply be reclaimed; a store wipe with reused game IDs may require a fresh world. Conflicting ownership/location/type/capacity/binding and nonempty unmapped chain inventories fail instead of being silently rewritten. Authored Unstable Fuel efficiency is 8%, while the bridge documents/validates a contract minimum of 10%; D1/D2 are compatible and the bridge does not silently change Unstable Fuel's authored value. Anchored Move bindings cannot be detached freely.

Coverage added: the `frontierSuiAssembly{Snapshot,Chain,Contents,Sync,Transactions,Reconcile,State,States,Supervisor,Admin,Energy,FuelBurn,Gate}.test.ts` suites, [frontierSuiStorageSync.test.ts](../../server/tests/frontierSuiStorageSync.test.ts), and projection/state-presentation tests.

### Network Node fuel and energy authority

Upstream's fuel transfer surface is expanded into persistent consumption and chain-backed fuel observations/intents. [networkNodeFuelRuntime.ts](../../server/src/services/frontier/networkNodeFuelRuntime.ts) burns online local fuel using authored efficiency and elapsed time, preserves fractional consumption progress across refuel/offline/restart, and takes dependent assemblies offline on exhaustion. Once confirmed Sui fuel is available, local ticks stop independently burning/replenishing it; explicit intents reconcile transfers against observed chain quantities.

Flag `172` is now a virtual Network Node fuel bay. Deposits consume ordinary inventory rows and increase reserve in one inventory transaction; withdrawals decrease reserve and materialize ordinary rows. Smart Storage and Industry reuse that boundary in both directions. Mixed fuels, invalid quantities/types, capacity overflow and conflicting pending intents are rejected before mutation. Activation, ownership, local visibility and interaction distance are enforced.

New [networkNodeEnergyConfig.ts](../../server/src/services/frontier/networkNodeEnergyConfig.ts), [networkNodeEnergyRuntime.ts](../../server/src/services/frontier/networkNodeEnergyRuntime.ts), and [networkNodeEnergyHoldRuntime.ts](../../server/src/services/frontier/networkNodeEnergyHoldRuntime.ts) add actual grid budgets and online-admission checks. Completed compatible assemblies attach to an eligible same-owner/same-system Network Node within 80 km, retaining valid saved bindings; manual disconnection persists. Energy requirements come from the pinned contracts manifest and are cross-checked against the extracted client catalog and all pages of the on-chain configuration. Zero-cost types must be explicitly represented. A deployment change invalidates the cache; unavailable/mismatched authoritative energy prevents new online transitions.

With Sui authority enabled, confirmed EnergySource production/reservation counters determine displayed availability, while pending committed online intents are considered during admission to prevent overbooking. Offline/online confirmations release/reserve power; a pending signature alone does not consume capacity. With synchronization disabled, deterministic local accounting can shed excess consumers when configured costs change. Fuel burn is independent of energy demand.

Fuel and power status are separate dimensions in durable operational signals: empty/low/normal fuel and offline/low/medium/high/over-limit usage. Rejected reservations publish their explicit reason without inflating confirmed consumption. The dApp energy API exposes status and serialized connect/disconnect operations, and also hosts the temporary Network Node remote-scanning API.

Evidence: the three energy modules, [networkNodeFuelRuntime.ts](../../server/src/services/frontier/networkNodeFuelRuntime.ts), [suiAssemblyState.ts](../../server/src/services/frontier/suiAssemblyState.ts), [suiAssemblyChain.ts](../../server/src/services/frontier/suiAssemblyChain.ts), [smartAssemblyEnergyEndpoints.ts](../../server/src/_secondary/express/smartAssemblyEnergyEndpoints.ts), and [world-contracts/config/assembly-energy.json](../../world-contracts/config/assembly-energy.json). Coverage added/expanded: `frontierNetworkNode{Energy,Fuel,FuelConsumption,ChainFuel}.test.ts`, [frontierAssemblyEnergyConfig.test.ts](../../server/tests/frontierAssemblyEnergyConfig.test.ts), [frontierSmartAssemblyEnergyApi.test.ts](../../server/tests/frontierSmartAssemblyEnergyApi.test.ts), and associated Sui energy/fuel/snapshot suites.

### Assembly deployment, lifecycle, templates and turrets

[deploymentRuntime.ts](../../server/src/services/frontier/deploymentRuntime.ts) adds physical footprint/overlap checks, placement previews, explicit pending activation timers, and rehydration of activation/construction presentation. Network Nodes and portable assemblies use the direct, material-consuming placement path; other authored Smart Assemblies use construction sites. Consumption/completion paths are hardened around actual deposited stacks and item-store writes. Online transitions now honor activation, fuel and grid constraints.

Dismantling is a new native service operation. It checks ownership/state, occupied berths and active Industry work; recovers materials and stored inventory into nearby capacity-bounded cargo containers separated by owner; clears relevant runtime state, requests and access; and preserves guest ownership. Construction cancellation uses the same dismantle boundary. Administrative removal also rejects occupied/active assemblies and coordinates lifecycle cleanup.

The runtime adds persistent-NPC construction primitives with current actor/incarnation checks, deterministic bounded placement attempts, construction material plans, idempotent job binding, direct/site placement, deposit/completion/state-control operations, and explicit faction registration. These are used by NPC jobs rather than impersonating a player login.

New [smartAssemblyConstructionTemplateStore.ts](../../server/src/services/frontier/smartAssemblyConstructionTemplateStore.ts) and [smartAssemblyConstructionTemplateRuntime.ts](../../server/src/services/frontier/smartAssemblyConstructionTemplateRuntime.ts) add revisioned, owner/principal-isolated reusable layouts and persisted execution plans. Nodes have relative transforms, dependencies, a supported placement mode and bounded loadout data; validation rejects duplicate/invalid nodes, unsupported direct-placement types, cycles and group overlap. A 60-second preview token pins the template revision and normalized composition; execution rechecks authoritative placement. Plans record per-node item IDs and states, handle resource/activation/authorization waits, can pause/resume/cancel, and queue excess construction-site nodes. The player scheduler admits at most one new site per pass and resumes persisted queues when the owner's template surface is reopened. Cancellation stops future work rather than automatically dismantling completed nodes.

Implementation limits matter: the expansive construction-template document is a design specification, not proof that every acceptance criterion ships. Current initial-inventory seeding accepts turret cargo; unsupported storage seeding is rejected. Fuel loadouts are Network Node-only, and desired online state can require a player signature. The implementation includes geometry and plan execution/RPCs but does not establish the complete proposed 3D editor, universal adapter catalog, arbitrary shared-template libraries, or every design-stage cleanup/metrics feature. Industry lane loadout metadata also feeds the separate NPC Industry child-job path.

New [smartTurretInventoryRuntime.ts](../../server/src/services/frontier/smartTurretInventoryRuntime.ts) validates turret cargo access; [smartTurretRuntime.ts](../../server/src/services/frontier/smartTurretRuntime.ts) adds scene-driven automatic turret and Field Sentry behavior. It resolves fitted weapon/charge profiles, candidates/aggression, targeting locks, shot cycles, damage/VFX and killmail participation. Smart turret priority comes from the new [suiTurretPriority.ts](../../server/src/services/frontier/suiTurretPriority.ts) resolver using typed candidate data and contract inspection; changed/stale priority snapshots clear targets rather than firing on unverified choices.

### Durable access grants, cross-owner custody, request queues and transponders

New [assemblyAccessRuntime.ts](../../server/src/services/frontier/assemblyAccessRuntime.ts) persists policies in `assemblyAccessPolicies` with player, NPC, tribe and canonical-faction principals; request/approve/deny/cancel/share/revoke/relinquish operations; audit events; expiry; and delegation attenuation. Capabilities distinguish GUI view, operate, inventory deposit/withdraw, configure and access management. Membership is resolved from current identities. Short-lived GUI tokens bind actor, session, assembly and policy revision. The owner has implicit rights; a delegated manager cannot amplify its rights or outlive a parent grant.

For portable/local assemblies the durable local policy is authoritative. Smart Assembly grants begin as unusable `local_projection_pending_chain` records. [suiAssemblyAccess.ts](../../server/src/services/frontier/suiAssemblyAccess.ts) derives expected object IDs itself and verifies live shared policy/grant objects and ancestor chains before promotion to `sui_confirmed`. A supplied object ID or client assertion alone does not grant rights.

New [assemblyCrossOwnerInventoryRuntime.ts](../../server/src/services/frontier/assemblyCrossOwnerInventoryRuntime.ts) implements a separate custody boundary for ship/storage and storage/storage transfers. It requires applicable direct chain grants and a finalized successful Sui transaction with the exact custody event/operation UUID, actor, endpoints, type and quantity. After asynchronous proof reads it rechecks local source/capacity/access, writes owner/location changes with a durable fingerprint/receipt, and rejects changed UUID reuse. Access alone does not change ownership. The native RPC is implemented; dedicated retail-client request/share/revoke and wallet custody UI remain work described by the access document.

New [smartAssemblyRequestRuntime.ts](../../server/src/services/frontier/smartAssemblyRequestRuntime.ts) provides a durable assembly-agnostic request bus: idempotent request UUIDs, queued/claimed/terminal lifecycle, renew/release, claim and request expiry, deterministic urgency/FIFO ordering, separate bitwise priority reasons, registered handlers, and monotonic signals with retention-gap detection. Signals publish after durable commit. Removal cancels participant work. Player RPCs require appropriate access and retain same-owner controls; trusted faction flows can opt into verified cross-owner delivery.

[suiAssemblyRequestLink.ts](../../server/src/services/frontier/suiAssemblyRequestLink.ts) attests public request/outcome commitments with an authorized world-server Sui PersonalMessage signature, binding the world, immutable request, exact assembly object references and deadlines; it rechecks authorization/proofs before claim/completion. [suiAssemblyActionQueue.ts](../../server/src/services/frontier/suiAssemblyActionQueue.ts) additionally supports deterministic on-chain queues/actions, payload commitments, bounded TTL/payload size, claim/release/complete transactions, canonical action-package identity and legacy access-package compatibility. These signatures/objects are not zero-knowledge proofs.

New [suiTransponderCommitment.ts](../../server/src/services/frontier/suiTransponderCommitment.ts) implements random 32-byte salts, canonical BCS and BLAKE2b-256 commitments, constant-time checking, deterministic tribe/faction object IDs, strict shared-object verification and author/rotate/revoke/transfer transaction builders. The code/salt are never sent in those chain transactions. They must be shared off chain; current faction codes remain local testing identifiers and commitment support is not automatic secure distribution. The faction task endpoint validates a current commitment and registration before writing a request, persisting public proof references rather than the secret code/salt.

### Industry recipes, per-lane escrow and production

Upstream [industryService.js](../../server/src/services/frontier/industryService.js) only recognized a fixed list of facilities and returned idle, empty details. New [industryStaticData.json](../../server/src/services/frontier/industryStaticData.json), [industryBlueprints.ts](../../server/src/services/frontier/industryBlueprints.ts) and [tools/frontier-static/extract-industry-static.py](../../tools/frontier-static/extract-industry-static.py) supply build-3502403 authored facilities, recipe inputs/outputs/runtime and resource hashes; recipe selection is checked against the facility catalog and persisted without replacing unrelated assembly metadata.

[industryRuntime.ts](../../server/src/services/frontier/industryRuntime.ts) and [industryInventoryAccess.ts](../../server/src/services/frontier/industryInventoryAccess.ts) implement blueprint selection, exact input deposits, input/output withdrawals, storage-to-Industry transfers, and emptying. Safe integer quantities, supported recipe types, per-type limits, capacity and specialized-hold restrictions are validated before atomic item movements. The resolver supports the active ship and appropriate holds, nearby owned cargo containers/Mobile Depots, Smart Storage partitions, Field Storage, turret cargo and virtual Network Node fuel according to the endpoint's authority. Transfers preserve exact moved quantities and do not jettison overflow. Live facility checks include ownership/authorized lane use, construction/activation, same system, active ship, visibility and range, with Creation-hosted facilities using their host-specific rules.

The final branch implements **independent lane recipe, escrow and production state**. Input flags are `20000 + 2 * (laneID - 1)` and output flags are the following odd values; lane 1 preserves legacy top-level fields and default RPC arguments. Each lane has its own selected blueprint and items. Nonportable Smart Industry defaults to four lanes, configurable from 1–16 by `frontierSmartIndustryJobLaneCount`, with valid facility-type overrides in `frontierSmartIndustryJobLaneCountByTypeID` and corresponding environment variables. Portable and Creation-hosted facilities remain single-lane. Lowering the configured count preserves already-paid work for settlement.

[industryProduction.ts](../../server/src/services/frontier/industryProduction.ts) consumes one paid run atomically when starting, stores deadline/job/recipe state, creates output at completion and admits another run only when permitted by input/output capacity and requested-run limits. Discontinue completes the paid run without consuming a subsequent run. Finite and continuous jobs, independent lane access policies (`owner`, `tribe`, `allowlist`, `public`), per-facility unique job IDs and durable executor correlations are supported. The worker in [industryProductionWorker.ts](../../server/src/services/frontier/industryProductionWorker.ts) starts explicitly after store initialization, discovers persisted active lanes and settles them every 250 ms with bounded catch-up. Invalid persisted state, changed recipes and offline facilities do not manufacture extra runs; paid products can settle while further runs stop. Active jobs block destructive lifecycle operations.

`industryNotifications.ts` and service marshalling publish inventory deltas, blueprint/item/production notices and lane-change events. Retail protobuf notices remain lane-1 compatibility projections; lane-aware callers read the complete lane state. Each changed inventory row gets its own change dictionary to avoid corrupting the client cache. [inventoryListenerRuntime.ts](../../server/src/services/frontier/inventoryListenerRuntime.ts) adds narrowly authorized, read-only quantity/capacity condition snapshots for task listeners without exposing arbitrary containers.

New [suiIndustrySnapshot.ts](../../server/src/services/frontier/suiIndustrySnapshot.ts), [suiIndustryChain.ts](../../server/src/services/frontier/suiIndustryChain.ts), [suiIndustrySync.ts](../../server/src/services/frontier/suiIndustrySync.ts), [suiIndustryDeployment.ts](../../server/src/services/frontier/suiIndustryDeployment.ts), and [suiIndustryStorageSync.ts](../../server/src/services/frontier/suiIndustryStorageSync.ts) mirror Industry sidecars with revision guards and fresh status verification. The final source explicitly uses `create_with_lane_states`/`sync_with_lane_states` and checks typed lane-state/production dynamic fields; it mirrors all authored lanes and preserves lane 1's legacy projection. A stale/missing old production projection cannot claim full synchronization. Industry/storage operations return committed game results separately from chain status.

### Storage, gateways and wallet-authenticated HTTP surfaces

Smart Storage retains per-character partitions but gains current authoritative chain-state refreshes, additional supported assembly/container endpoints, atomic fuel-bay integration, pending transfer recovery lookup and a longer completed-operation replay window. Prepared authorizations expire after two minutes; completed transfer receipts are kept in memory for 24 hours. A repeated identical signed UUID returns the original result without moving items again during that window. Those HTTP/runtime receipts are not a durable server-restart ledger; saved inventory and the Sui transaction journal are durable. [fieldStorageInventoryRuntime.ts](../../server/src/services/frontier/fieldStorageInventoryRuntime.ts) adds owner-only local cargo access for the specific off-chain deployable component combination, with activation/online/range/capacity checks.

New HTTP APIs are mounted by the Express gateway. Each uses scoped wallet challenges/sessions, maps the wallet to an active game character, checks live authority again around queued/asynchronous work, applies origin allowlists and returns controlled errors. The authorization signature does not itself imply a submitted chain transaction.

### Smart Gates and one-way catapults

Paired gates existed upstream. The branch adds explicit link-status/query helpers and direct runtime link/unlink entry points for the dApp, stronger asynchronous ownership/snapshot validation, pending-transition invalidation and actual chain mirroring. Link constraints include completed/offline same-type owned gates in distinct systems within the client-authored range, with exact-boundary distances allowed. The chain bridge validates both endpoints and uses a signed distance proof tied to object IDs, committed locations, wallet, maximum distance and deadline. Local completion and chain-pending results remain distinguishable; retrying sync does not repeat the gameplay link mutation.

Slingshots now have one-way Smart Catapult behavior: available-system selection, set/clear destination and system jump. They need no destination assembly. Owner route edits require an offline source and a valid distinct in-range system; an online configured source can carry an active ship in that source system and applies the normal jump cloak. [suiAssemblyContents.ts](../../server/src/services/frontier/suiAssemblyContents.ts)/[suiAssemblyChain.ts](../../server/src/services/frontier/suiAssemblyChain.ts) attach a deterministic independently packaged catapult sidecar to the base Gate, with revision-guarded route state. Client-authored ranges for the current catalog distinguish small 65-light-year and heavy 365-light-year types; chain range configuration is checked/configured on mutations rather than silently replaced by a read.

### Documentation inconsistencies that affect interpretation

Several checked-in documents describe earlier implementation stages and must not be read as a precise inventory of the final branch:

- [docs/FRONTIER_INDUSTRY_INVENTORY.md](../../docs/FRONTIER_INDUSTRY_INVENTORY.md) says the inventory work does not manufacture outputs; [industryProduction.ts](../../server/src/services/frontier/industryProduction.ts) and the production worker now do.

- [docs/FRONTIER_WORLD_SYNC.md](../../docs/FRONTIER_WORLD_SYNC.md) describes a base world plus five feature packages/six-package publish; the pinned contracts tree and feature readers now contain the base plus ten feature packages, including action/automation packages.

The runtime implements a meaningful subset; that document's entire planned UI, adapter, sharing and hardening scope should not be counted as finished code.

These discrepancies are recorded here rather than treating document prose or unverified deployment assertions as evidence of shipped behavior.
